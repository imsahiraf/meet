# Meet v1.0

# Laravel Development Guide (LDG)

## LDG - Part 4

## Models, Eloquent Relationships & Database Integration

**Version:** 1.0

**Framework:** Laravel 12

**Database:** MySQL 8+

---

# 1. Purpose

This document defines the standards for Eloquent models, database relationships, attribute handling, query optimization, factories, seeders, and database interaction across the Meet platform.

Models shall represent domain entities while keeping business logic inside the Service Layer.

---

# 2. Model Philosophy

Models shall:

* Represent database entities
* Define relationships
* Define scopes
* Define casts
* Define attribute accessors
* Define attribute mutators

Models shall not contain complex business workflows.

---

# 3. Model Directory Structure

```text id="m4j2xp"
app/

Models/

User.php

Contact.php

Chat.php

Message.php

Group.php

Meeting.php

MeetingParticipant.php

File.php

Notification.php
```

Large modules may organize models into subdirectories.

---

# 4. Base Model

A shared base model may provide:

* UUID generation
* Audit support
* Soft Deletes
* Common scopes
* Shared traits

Application-specific reusable behavior should be centralized where appropriate.

---

# 5. Primary Keys

Supported strategies

* Auto Increment Integer
* UUID

For public-facing resources, UUIDs are recommended to avoid exposing sequential identifiers.

---

# 6. Fillable & Guarded

Every model shall explicitly define mass assignment protection.

Preferred approach

* `$fillable`

Avoid leaving models completely unguarded unless there is a well-documented reason.

---

# 7. Hidden Attributes

Sensitive fields shall be hidden from serialization.

Examples

* Password
* Remember Token
* Internal Security Fields

Hidden attributes shall never be exposed through API Resources.

---

# 8. Attribute Casting

Examples

* Boolean
* Integer
* Decimal
* Array
* JSON
* Date
* DateTime

Native Laravel casting shall be used whenever possible.

---

# 9. Accessors

Accessors may be used for:

* Full Name
* Avatar URL
* Display Name
* Human Readable File Size

Accessors shall not execute expensive database queries.

---

# 10. Mutators

Mutators may be used for:

* Normalizing Names
* Formatting Phone Numbers
* Hashing Passwords (where appropriate)

Mutators should remain deterministic and lightweight.

---

# 11. Eloquent Relationships

Supported relationship types

* One to One
* One to Many
* Many to Many
* Has One Through
* Has Many Through
* Morph One
* Morph Many
* Morph To

Relationships shall use descriptive method names.

---

# 12. User Relationships

Examples

User

* Contacts
* Chats
* Groups
* Meetings
* Notifications
* Devices
* Files

The User model acts as the central entity for authenticated features.

---

# 13. Group Relationships

Group

* Members
* Messages
* Polls
* Events
* Files
* Owner

Group membership shall be modeled through a dedicated pivot or membership table.

---

# 14. Meeting Relationships

Meeting

* Host
* Participants
* Chat
* Whiteboard
* Recordings (Future)

Meeting-related entities shall remain logically grouped.

---

# 15. File Relationships

File

* Owner
* Shared Users
* Meeting
* Chat
* Group

Files may be associated with multiple domain entities where appropriate.

---

# 16. Query Scopes

Local scopes may include:

* Active
* Verified
* Public
* Archived
* Scheduled

Global scopes shall be used sparingly and documented.

---

# 17. Soft Deletes

Soft Deletes shall be enabled for resources that may require restoration.

Examples

* Users
* Groups
* Files
* Meetings

Permanent deletion shall be restricted to authorized administrative workflows.

---

# 18. Eager Loading

Use eager loading to prevent N+1 query issues.

Relationships shall be loaded only when required.

Unnecessary eager loading should be avoided to reduce memory usage.

---

# 19. Query Optimization

Recommendations

* Use indexes effectively.
* Select only required columns.
* Paginate large datasets.
* Avoid repeated database queries.
* Cache frequently accessed configuration where appropriate.

Performance considerations shall be included during feature development.

---

# 20. Database Transactions

Models participating in multi-step operations shall be coordinated through service-managed database transactions.

Models shall not begin or commit transactions directly.

---

# 21. Factories

Factories shall exist for all major models.

Examples

* UserFactory
* GroupFactory
* MeetingFactory
* FileFactory

Factories support testing and development seeding.

---

# 22. Seeders

Seeders may include:

* Roles
* Permissions
* Administrator Account
* Demo Users
* Sample Groups
* Sample Meetings

Development and production seeders should be separated where practical.

---

# 23. Observers

Model observers may be used for:

* Audit Logging
* Cleanup Tasks
* Notifications
* Cache Invalidation

Business workflows should generally remain in services unless the observer behavior is clearly model-centric.

---

# 24. Model Testing

Every model shall be tested for:

* Relationships
* Scopes
* Accessors
* Mutators
* Casts
* Soft Deletes

Factories shall be used extensively in automated tests.

---

# 25. Future Expansion

The model architecture supports future capabilities including:

* Multi-Tenant Relationships
* Audit Versioning
* Advanced Polymorphic Features
* Read Replicas
* Database Sharding (where justified)

These enhancements shall be introduced without disrupting existing model conventions.

---

# LDG-4 Summary

This document defines the standards for Laravel Eloquent models, relationships, attribute handling, scopes, soft deletes, query optimization, factories, seeders, observers, and database integration. It provides a consistent data layer that supports scalability, maintainability, and efficient database access across the Meet platform.
