# 1. Purpose

This document serves as the master blueprint for AI-assisted development of the Meet platform.

It consolidates all AI development rules, implementation workflows, documentation dependencies, quality standards, and governance principles defined throughout the CDM.

---

# 2. End-to-End AI Development Workflow

Every implementation request shall follow:

```text
Understand Requirement
        ↓
Review SRS
        ↓
Review DDS
        ↓
Review RAS
        ↓
Review UDS
        ↓
Review LDG
        ↓
Review CDM
        ↓
Identify Dependencies
        ↓
Generate Code
        ↓
Generate Tests
        ↓
Validate Architecture
        ↓
Update Documentation
        ↓
Final Review
```

The AI shall not skip required review stages when the relevant documentation exists.

# 3. Documentation Dependency Matrix

The AI shall use the following documentation hierarchy:

| Priority | Document | Purpose                |
| -------- | -------- | ---------------------- |
| 1        | SRS      | Business requirements  |
| 2        | SAD      | System architecture    |
| 3        | LAD      | Laravel architecture   |
| 4        | DAD      | Database architecture  |
| 5        | DDS      | Database design        |
| 6        | RAS      | API contracts          |
| 7        | UDS      | UI/UX standards        |
| 8        | LDG      | Laravel implementation |
| 9        | CDM      | AI governance          |

No generated implementation shall intentionally contradict higher-priority documentation.

# 4. AI Generation Checklist

Before completing any feature, verify:

* Requirement satisfied
* Database updated (if required)
* Model implemented
* Repository implemented
* Service implemented
* Policy implemented
* Validation implemented
* Controller implemented
* API Resource implemented
* Routes implemented
* Events implemented
* Listeners implemented
* Queue Jobs implemented (if required)
* Tests prepared
* Documentation updated

Items that are not applicable shall be explicitly identified rather than silently omitted.

---

# 5. Module Completion Rules

A module is complete only when:

* Architecture follows project standards.
* Business rules are implemented.
* Validation is complete.
* Authorization is enforced.
* Responses are standardized.
* Tests are prepared.
* Documentation is synchronized.

Partial implementations shall not be represented as production-ready.

---

# 6. Regeneration Workflow

When modifying an existing module, the AI shall:

1. Review the existing implementation.
2. Compare it with current documentation.
3. Identify required changes.
4. Preserve compatible interfaces where practical.
5. Explain any breaking changes.
6. Update tests.
7. Update documentation.

Regeneration shall minimize unnecessary changes.

---

# 7. Decision Rules

The AI shall:

* Prefer reuse over duplication.
* Prefer framework conventions over custom implementations.
* Prefer maintainability over brevity.
* Prefer explicit behavior over hidden complexity.
* Prefer documented requirements over assumptions.

Where documentation is incomplete, the AI shall state assumptions clearly.

---

# 8. Security Governance

Every generated module shall verify:

* Authentication
* Authorization
* Input Validation
* Output Safety
* Secure File Access
* Logging of Significant Security Events

Security shall be reviewed before release readiness.

---

# 9. Performance Governance

Every generated module shall evaluate:

* Database Queries
* Eager Loading
* Pagination
* Queue Usage
* Cache Opportunities
* Background Processing

Performance optimizations shall preserve functional correctness.

---

# 10. Documentation Governance

All implementation changes shall update the relevant technical documentation.

Documentation updates include:

* Architecture
* API
* Configuration
* Operational Notes
* Testing Notes

Documentation shall remain consistent with the implementation.
