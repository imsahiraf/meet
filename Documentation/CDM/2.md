# Meet v1.0

# Claude Development Manual (CDM)

## CDM - Part 2

## Backend Generation Workflow

**Version:** 1.0

**Target AI:** Claude (Latest Version)

**Framework:** Laravel 12

---

# 1. Purpose

This document defines the exact workflow that the AI shall follow while generating backend modules for the Meet platform.

The objective is to ensure that every module is produced in a deterministic, repeatable, and production-ready manner.

No module shall be considered complete until all required files have been generated, integrated, tested, and documented.

---

# 2. Backend Generation Philosophy

The AI shall generate backend modules:

* Incrementally
* Deterministically
* Module by Module
* Without Breaking Existing Code
* Following Laravel Best Practices

Each generated module shall integrate cleanly with previously completed modules.

---

# 3. Module Generation Order

The backend shall be implemented in the following sequence:

### Foundation

* Authentication
* Users
* Roles
* Permissions

### Communication

* Contacts
* Chats
* Messages

### Collaboration

* Groups
* Meetings
* Voice Calls
* Video Calls

### Productivity

* Calendar
* Files
* Notifications

### Administration

* Dashboard
* Reports
* Analytics
* Security
* Backup
* Archive

This order minimizes dependency conflicts.

---

---

# 5. Migration Rules

Before creating a migration, the AI shall verify:

* Table does not already exist.
* Required relationships are documented.
* Indexes are defined.
* Foreign keys are valid.
* Naming follows project conventions.

Schema duplication shall be avoided.

---

# 6. Model Rules

Every model shall include:

* Relationships
* Fillable Attributes
* Hidden Fields
* Casts
* Scopes (where applicable)
* Soft Deletes (if required)

Business logic shall remain outside the model.

---

# 7. Repository Rules

Repositories shall:

* Encapsulate database queries.
* Support pagination.
* Support filtering.
* Support searching.
* Remain persistence-focused.

Repositories shall not contain presentation logic.

---

# 8. Service Rules

Services shall:

* Implement business rules.
* Coordinate repositories.
* Dispatch events.
* Manage transactions.
* Throw domain-specific exceptions.

Services shall be the primary location for business workflows.

---

# 9. Controller Rules

Controllers shall:

* Receive validated requests.
* Invoke services.
* Return API Resources.
* Return standardized responses.

Controllers shall remain thin.

---

# 10. Route Generation

Routes shall:

* Follow REST conventions.
* Use API versioning.
* Apply appropriate middleware.
* Follow naming standards.

Routes shall be grouped by module.

---

# 11. Validation Workflow

The AI shall generate:

* Form Requests
* Validation Rules
* Custom Rules (when required)
* Validation Messages

Validation logic shall not be duplicated across controllers.

---

# 12. Authorization Workflow

The AI shall generate:

* Policies
* Policy Registration
* Permission Checks

Every protected operation shall include authorization.

---

# 13. Event Workflow

Business events shall be generated for significant actions.

Examples

* UserRegistered
* MeetingCreated
* FileUploaded
* NotificationCreated

Events shall remain descriptive and domain-oriented.

---

# 14. Queue Workflow

Background jobs shall be created for:

* Email Delivery
* Notification Delivery
* File Processing
* Report Generation
* Backup Operations

Long-running tasks shall not block HTTP requests.

---

# 15. API Resource Workflow

Resources shall:

* Transform responses.
* Hide internal attributes.
* Maintain consistent JSON.
* Support future extensibility.

Resources shall not contain business logic.

---

# 16. Testing Workflow

Each module shall include:

* Unit Tests
* Feature Tests
* Authorization Tests
* Validation Tests
* Integration Tests (where applicable)

Tests shall validate the generated implementation rather than assumptions.

---

# 17. Documentation Workflow

For every completed module generate:

* Technical Notes
* Configuration Requirements
* Testing Notes
* Operational Notes

Documentation shall reflect the implemented behavior.

---

# 18. Completion Criteria

A module is complete only when:

* All required files exist.
* Tests pass.
* Routes function.
* Validation is implemented.
* Authorization is enforced.
* Documentation is updated.

Partial implementation shall not be marked as complete.

---

# 19. Regeneration Rules

If regeneration is required, the AI shall:

* Preserve existing architecture.
* Avoid duplicate files.
* Preserve database compatibility where possible.
* Explain breaking changes before applying them.

Regeneration shall minimize disruption.

---

# 20. AI Decision Rules

When documentation is complete:

* Do not invent features.
* Do not ignore documented requirements.
* Do not replace existing architecture.
* Prefer reuse over new implementations.

If information is missing, explicitly identify the gap instead of guessing.

---

# 21. Future Expansion

The generation workflow supports future capabilities including:

* Plugin Modules
* Enterprise Extensions
* AI Services
* Public APIs
* Multi-Tenant Deployments

These additions shall integrate into the existing workflow without restructuring completed modules.

---

# CDM-2 Summary

This document defines the backend generation workflow for AI-assisted development of the Meet platform. It specifies the module implementation sequence, file creation order, validation, authorization, testing, documentation, regeneration strategy, and completion criteria required for consistent, production-ready backend generation.
